# Semantic Search Engine

A lightweight, CPU-based semantic search engine built with Python, Sentence Transformers, and NumPy for **PromptForge GenAI & LLM Virtual Internship — Week 2: Embeddings & Semantic Search**.

The project indexes 40 student tech-support FAQ records, converts each record into a 384-dimensional embedding, caches the dataset vectors, and retrieves the top three records for a natural-language query using cosine similarity. A simple keyword-overlap baseline is included to compare exact word matching with embedding-based retrieval.

## Features

- **Local sentence embeddings:** Uses `sentence-transformers/all-MiniLM-L6-v2` to represent FAQ text as 384-dimensional vectors.
- **Embedding fundamentals demo:** Prints vector shapes and compares cosine similarity for related and unrelated sentences.
- **40-record FAQ dataset:** Structured JSON records with an ID, category, question, and answer.
- **Reusable embedding cache:** Saves dataset vectors to `embeddings/dataset_embeddings.npy` and cache metadata to `embeddings/embedding_metadata.json`.
- **Semantic search CLI:** Embeds a query, ranks cached vectors by cosine similarity, and displays the top three FAQ matches with scores.
- **Keyword baseline:** Ranks the same FAQ dataset by query-token overlap.
- **Five-query comparison:** Runs the same queries through both methods and records the current experiment results in `comparison.md`.
- **Cache validation:** Checks the dataset fingerprint, model name, vector dimensions, and numeric values before search.
- **CPU-first and API-free:** No Groq API key, paid inference endpoint, hosted vector database, or GPU is required.

## Technology stack

| Technology | Purpose |
|---|---|
| Python 3.10+ | Application logic and command-line interface |
| Sentence Transformers | Loads the pretrained embedding model and encodes text locally |
| `all-MiniLM-L6-v2` | Produces 384-dimensional sentence embeddings |
| NumPy | Stores vector arrays, calculates cosine similarity, and reads/writes the `.npy` cache |
| JSON | Stores the FAQ dataset and cache metadata |
| `unittest` | Tests core dataset and similarity/search helpers |
| Git and GitHub | Version control and public project submission |

The tested environment for this project used Python 3.13 on Windows and CPU inference. The first package installation and model download require an internet connection. Once downloaded, embedding and search inference run locally. The model's Hugging Face model card lists an Apache-2.0 license; review the model card for its usage details.

## Setup on Windows PowerShell

Run these commands from the project directory, where `README.md` is located.

```powershell
py -3.13 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
```

If the Python launcher does not recognize `-3.13`, use `py -m venv .venv` to create the environment with the installed Python version. If PowerShell blocks virtual-environment activation, the script execution policy can be adjusted for the current terminal session:

```powershell
Set-ExecutionPolicy -Scope Process -ExecutionPolicy RemoteSigned
.\.venv\Scripts\Activate.ps1
```

The first model load downloads the pretrained weights. This can take longer than later runs and requires internet access. Inference is configured to use the CPU.

## Run the project

### 1. Run the unit tests

```powershell
python -m unittest discover -s tests -v
```

The five core unit tests passed in the development run.

### 2. Demonstrate embedding basics

```powershell
python embedding_demo.py
```

The four-sentence experiment produced an embedding matrix of shape `(4, 384)`. In the recorded run, the two related-sentence comparisons scored `0.6369` and `0.6692`, while the laptop-battery versus boiling-water comparison scored `0.0024`. These values are cosine similarity scores, not probabilities.

### 3. Embed and cache the FAQ dataset

```powershell
python embed_data.py
```

The script validates the data, embeds the question, answer, and category text for each record, and saves the normalized vectors. The recorded run produced an embedding matrix of shape `(40, 384)`.

Run this command again after changing `data/dataset.json`. The search program checks a SHA-256 dataset fingerprint and will report a stale cache rather than silently using vectors for a different dataset.

### 4. Start interactive semantic search

```powershell
python search.py
```

Enter a natural-language query to view the three highest-ranked FAQ records. Each result includes its ID, category, question, answer, and cosine similarity score. The score is a relative ranking signal, not a confidence percentage.

CLI commands:

| Command | Purpose |
|---|---|
| `/help` | Displays usage information |
| `/quit` or `/exit` | Ends the session |
| `quit`, `exit`, or `0` | Also ends the session |

### 5. Compare keyword and semantic retrieval

```powershell
python compare_search.py
```

The script runs five fixed queries through semantic search and keyword-overlap search, prints a concise summary, and updates the generated-results section in `comparison.md`. The manual interpretation in that file reflects the observed run and highlights both successes and errors.

## Recorded experiment results

The following results were observed on a Windows CPU run with the included dataset and model:

| Test query | Semantic top result | Similarity | Keyword baseline | Observation |
|---|---|---:|---|---|
| `My notebook goes dead before the lecture ends.` | FAQ025 — screen sharing during an online class | 0.2884 | No match | The top semantic result was incorrect. In the interactive top-three output, the battery FAQ (FAQ011) appeared at rank 3. |
| `My handset cannot browse while I am indoors.` | FAQ009 — website works on mobile data but not Wi-Fi | 0.3825 | No match | The semantic result was partially relevant to a connectivity problem, but did not fully resolve the ambiguity in the query. |
| `I made a mistake and now the earlier material is gone.` | FAQ018 — recover edits from a document closed without saving | 0.3146 | FAQ025 — screen sharing during an online class | Semantic retrieval returned a relevant document-recovery result; keyword search matched the word `material` in an unrelated FAQ. |
| `The machine is scorching and no longer responds.` | FAQ021 — printer not printing | 0.3572 | FAQ005 — sign out of an account on another device | Neither top result was relevant to the combined overheating/unresponsive-device query. |
| `Booting is painfully sluggish, and the desktop takes forever to appear.` | FAQ013 — computer starts slowly | 0.5732 | No match | Semantic retrieval found the intended startup-performance FAQ when keyword search had no match. |

This is a small, manually inspected experiment rather than a formal benchmark. The semantic top result was clearly relevant for two queries, partly relevant for one query, and poor for two queries. The results demonstrate why retrieval quality must be checked rather than assumed: embeddings can retrieve useful paraphrases, but may also rank unrelated entries first. The detailed query-by-query notes are in [`comparison.md`](comparison.md).

## Implementation notes

- Dataset text is normalized consistently for search-related processing.
- The embedding model is loaded lazily for query search and uses CPU inference.
- Dataset embeddings are cached; the full dataset is not re-embedded for each query.
- The keyword baseline is intentionally simple: it removes common stop words and ranks entries by the fraction of meaningful query tokens that overlap the FAQ text. It does not handle synonyms or understand context.
- The embedding input includes each FAQ's question, answer, and category. This helps retrieval use more of the FAQ content, but an answer or category can also affect the ranking.
- The current system retrieves FAQ records only. It does not generate new answers using an LLM and is not yet a complete RAG chatbot.

## Scope and limitations

The project demonstrates the retrieval component of a Retrieval-Augmented Generation (RAG) pipeline. It is designed for a small instructional dataset and uses brute-force cosine comparisons against the in-memory matrix. It does not use a vector database, approximate nearest-neighbor index, web interface, or cloud service. Search results depend on the dataset, query wording, embedding model, and ranking method. The five-query comparison is useful for exploration but is too small to establish general search accuracy.

A later iteration could improve the FAQ records, add labelled relevance judgments, test more paraphrases, and compare top-k retrieval quality. A vector database such as ChromaDB could be explored in a later task; NumPy is used here to keep the embedding and cosine-similarity mechanisms explicit.
